容器之间，实际连接什么？

同一服务的多个 View 通过 task_id、service_version、action_id 与状态 revision 关联；动作事件回到运行时，真实回执更新 TaskState，再同步到窗口、Widget 与 VUI。

ActionEvent → Runtime → Receipt → TaskState → Window / Widget / VUI
跨服务协作，如何接上？

通过版本化能力端口、事件订阅或经授权的服务调用联动，保留作用域与输入输出类型。跨服务可建立有 trace 关联的子任务，不把任意应用的数据或内存自动共享。

画板关闭，服务会停止吗？

视图显隐、容器生命周期和任务生命周期分别定义。隐藏 Widget 或窗口不隐式取消任务；暂停、恢复与停止由运行时结合能力契约执行，并向用户说明实际结果。

01 · 产品定义

Lego OS 是面向个人 AI 设备与智能眼镜的开放服务系统。它把人的意图、可组合的能力、持续运行的服务与一致的交互语言连接起来，让用户从现成服务开始，也能沿着好奇心创造属于自己的使用方式。

系统的核心转变是：人不必先学习如何操作，服务与系统应当学会理解人。 用户可以表达目标、选择方式、委托执行，并始终保有纠正和停止的权利。

Lego OS 中的 OS，指在既有操作系统与设备能力之上，统一服务组织、任务运行、容器协作和人机交互的系统层。它既服务日常使用，也为探索和创造提供空间。

Build freely. Try safely. Discover joyfully. Delegate with confidence.

1.1 产品所承载的三种价值

价值对人的意义对系统的要求
好奇可以被探索可以试一试，不必先成为专家现成入口、可预览、可撤回的试用边界
创意可以被做出来表达核心需求，就能形成可用服务AI 承担细节补全，积木承载能力，容器承载体验
日常可以放心委托不必持续盯着每一步，也知道事情如何了真实执行、明确状态、适时反馈、持续可控

1.2 一个完整的系统命题

理解 → 表达 → 服务 → 反馈 → 再理解。

理解人的目标与情境；帮助人表达和塑造体验；把意图落实为真实服务；把结果与不确定性带回用户；允许用户在使用中持续调整。这是日常交互的闭环，也是创造与使用的闭环。

02 · 设计理念

2.1 开放能力，统一语言

系统不规定所有创作工具，也不包办所有服务内部的编排。用户可以使用 AI、创意工坊、第三方工具或 SDK 进行创作。系统承接符合约定的能力与服务，让它们进入可理解、可管理、可协作的运行环境。

开放的是创作方式、能力组合与表现形式；统一的是能力契约、运行语义、授权边界、任务状态与基础交互语言。

2.2 用户提供需求核心，系统承担专业复杂度

用户不需要同时具备交互、产品、合规、研发和测试思维。AI 创作助手应将需求整理为可讨论的服务定义，补全输入、处理、输出、异常和控制方式；遇到影响目标与权利的选择，再向用户澄清。

技术细节可以被系统承担，目标与选择不能被系统代替。重要决定必须能让用户理解，默认配置也必须可以被查看和调整。

2.3 积木具有结构，组合创造可能

Lego / Minecraft 的意义在于：少量清晰规则支持丰富结果。每块积木具有明确用途、接口和边界；不同形态的积木承担不同职责。系统不要求用户理解每一粒“尘埃”，也不把所有能力压成没有差异的通用节点。

2.4 自由探索与可靠使用共存

探索环境允许试验、预览与局部失败。进入日常使用的服务，则需要明确自己的能力、边界、控制方式和实际结果。探索可以轻松，委托必须有依据。

2.5 个人化由用户主导

用户可以选择服务、工具、模型、呈现方式与自动化程度。人格与表达风格是可以选择的体验属性，不能改变权限、事实或执行结果。系统提供指导，也给用户保留不被强制个性化的空间。

03 · 设计目标与系统承诺

目标系统应呈现的行为
自然表达语音、手势、文字、界面与事件都能进入一致的意图体系；有歧义时澄清
易于创造从需求核心或现成服务开始，逐步形成可预览、可使用、可修改的服务
真正可用创作结果包含运行行为、真实能力、数据与异常处理，完成 Create–Use 闭环
跨界面连续窗口、Widget、VUI 与其他视图可以表达同一任务，不制造相互矛盾的状态
委托可控用户知道正在做什么、已做什么、还需要什么，并能调整或停止后续执行
开放而一致不同来源的服务保持各自特色，同时遵守共同的交互和权限语义
适合眼镜系统尊重注意力、现实环境与隐私，选择合适的反馈时机与模态

这些目标由系统规则支持，不依赖每个创作者重新设计一套可靠性与交互体系。

04 · 核心对象：系统究竟管理什么

对象定义关键关系
Capability / 原子能力具有明确输入、输出、作用与约束的可复用能力可以被服务引用；并非每个能力都面向用户直接展示
Service / 服务面向某类目标的持续可用定义，包含触发、行为、能力依赖、数据与交互约定同一服务可被多次使用，形成多个 Task
Agent / 智能代理在授权范围内理解目标、形成计划、调用能力并根据反馈调整的行为角色使用服务与能力；受统一任务和策略约束
Task / 任务一次具体目标的运行实例具有身份、状态、进度、回执和生命周期
Container / 容器提供表现、交互或执行环境，并声明宿主边界的画板可承载服务视图或逻辑；不能与 Task 混同
View / 视图某个任务或服务在特定界面与模态中的表达同一 Task 可以有多个 View
Context / 上下文与当前理解和执行有关、有来源与时效的信息供理解与决策使用；不自动成为长期记忆
Policy / 策略对授权、注意力、数据、资源和行为边界的系统规则贯穿服务、任务、容器和能力调用
Package / 发布包一份可识别、可版本化、可分发的能力或服务定义定义可被安装和更新的对象，与运行中的实例分离

积木提供能力，服务组织行为，任务承载一次执行，容器提供环境，视图表达状态。

一个 Widget 可以启动新任务，也可以显示已有任务；一个窗口可以承载复杂服务；VUI 可以接续它们的交互。它们是否属于同一任务，取决于明确的绑定关系，不能仅凭界面相似来判断。

05 · 总体架构：开放创作，可信运行

5.1 三个协作面

协作面核心职责与其他面的关系
开放创作面需求表达、服务构建、预览、私用、发布与生态分发任意兼容工具均可接入；产物通过共同契约进入系统
服务运行与体验面理解目标、组织任务、调用能力、承载容器、表达结果对服务如何进入日常使用负责
贯穿治理面身份、授权、数据边界、注意力、资源、隔离与版本治理持续约束前两者，不能被创作工具或服务绕过

5.2 四层系统框架

层级职责面向上层提供什么
系统交互与体验层输入路由、容器宿主、语义视图、焦点与注意力、统一控制一致而可定制的人机交互
服务与 Agent 层服务发现、意图理解、澄清、计划与重规划、受权上下文与目标对应的服务选择和计划提案
任务运行核心任务状态、步骤推进、策略判定、能力路由、结果与恢复可追踪、可控制、有真实回执的运行过程
能力执行与适配层原生能力、受控代码、外部连接器、SDK 服务的执行与适配符合契约的能力调用和实际结果

既有 OS 与设备平台提供显示、音频、传感、网络、存储和设备管理等基础能力。上述分层描述职责关系，不限定进程数量、设备位置或技术选型。

5.3 四条不可混淆的边界

  • 计划与执行分开。 Agent 形成计划提案；任务运行核心依据授权与状态决定是否执行。
  • 执行与呈现分开。 任务事实来自实际能力与回执；界面表达这些事实，不能凭文案宣告成功。
  • 内部编排与系统协作分开。 第三方可以自行组织内部逻辑；需要与系统协作的能力遵守公共契约。
  • 平台规则与创作积木分开。 创作者可以提出权限与资源需求，不能自行决定绕过系统规则。

5.4 两种受控运行方式与开放接入

声明式服务以能力和流程定义描述行为；受控代码服务在隔离边界内表达更自由的逻辑。两者共享任务、授权、状态与控制语义。独立 SDK 应用可以在官方容器之外形成自己的体验，并按需接入系统协议。

表现容器与运行方式是两个维度：一个窗口不等于一种执行引擎，一种执行引擎也不限定唯一界面。

06 · 原子积木：八类职责

类别核心问题典型内容
I / 输入与感知什么进入系统？语音、图像、位置、动作与外部事件
P / 理解与转换信号意味着什么？转写、识别、抽取、翻译、意图与指代解析
F / 流程与连接何时推进，如何连接？条件、顺序、并行、等待、定时、澄清
D / 数据与状态什么需要被保留与共享？任务状态、服务数据、受权上下文、个人记忆
C / 外部连接器怎样与外部系统协作？账号、协议适配、外部查询、回执与远程状态
A / 动作与执行什么实际发生了变化？写入、采集、控制、调用与远程动作
O / 输出与呈现如何向人表达？卡片、窗口、Widget、语音、空间内容、触觉与通知
G / 系统治理怎样始终在边界内运行？权限、注意力、资源、兼容、版本、追踪与隔离

这些类别描述职责，不能只靠颜色区分。同一设备或业务功能可能涉及多类积木：相机取帧属于输入，理解画面属于处理，保存照片属于动作，展示照片属于输出。

一块可组合积木需要表达：它做什么、接受什么、返回什么、需要什么授权、会改变什么、何时失败，以及如何停止或恢复。系统可根据这些定义帮助用户组合，用户不必逐项手工填写专业契约。

流程原语和治理能力是系统构成的一部分；它们不必全部开放为创作者可任意改写的业务积木。具体能力目录见第 15 章。

07 · 容器：为积木提供画板

容器定义可创作的空间、宿主提供的能力，以及系统始终保留的边界。自由度可以不同，控制语义应保持一致。

7.1 有限边界：扩展已有系统服务

宿主类型可定制内容宿主保留的责任
系统皮肤视觉主题、材质、动效和呈现风格信息层级、可辨识性与关键控制
看板与 Widget数据绑定、组件组合、快捷动作生命周期、任务绑定、布局和注意力边界
宠物与陪伴形象外观、表达和互动内容系统状态、资源与交互秩序
VUI 服务扩展服务意图、对话内容、可调用能力会话归属、打断、授权和任务控制
拍摄与 AR 滤镜画面处理、叠加与交互效果采集授权、场景边界与拍摄状态

不同扩展点具有各自契约。修改外观、增加业务逻辑与新增敏感输入是不同程度的扩展，不因都位于同一宿主内就获得相同权限。

7.2 相对自由：自定义服务窗口

用户可以在窗口内选择输入类型、处理方式、数据组织、交互流程与输出样式，形成接近独立应用的服务体验。它可以由现成积木组合，也可以包含受控的自定义逻辑。

“相对自由”意味着创作空间开放，同时仍遵守系统的权限、资源、任务和基础交互规则。窗口本身不授予额外设备权限。

7.3 官方容器之外：Open SDK

深度开发者可以用 SDK 创建独立应用、服务与工具，拥有自己的界面和内部组织方式。SDK 开放不是把一切塞入同一个官方窗口，而是提供能力调用、服务声明、任务状态与语义交互等协作接口。

系统应明确每个第三方对象支持哪一层协作：启动入口、能力调用、任务状态，或更完整的语义交互。能启动，不自动代表可以跨视图接续完整任务。

7.4 容器之间可以协同

一个自定义窗口服务，可以同时提供自己的 Widget，并将合适的意图和反馈连接至系统 VUI。窗口、Widget 和 VUI 读取同一任务的有效状态，各自按场景呈现；操作回到对应任务，经系统判定和执行后再更新各视图。

不同服务之间通过声明的数据、事件与动作协议协作。它们可以关联任务，但不因此共享全部数据、记忆或权限。

08 · 统一交互语言

定制化不要求每个服务重新发明基本操作。系统为理解、选择、委托、纠正、打断和恢复提供共同语义；容器可以用不同形式表达它们。

交互语义用户应能理解什么系统责任
理解与澄清系统理解的目标、关键约束与未确定项保留用户原意，只询问影响结果的必要问题
选择与预览有什么选项，选了会发生什么呈现差异与后果，支持适度试用
确认与委托这次允许做什么，允许持续多久将授权绑定到具体对象、范围与情境
进度与结果正在做、等待中、已完成或无法确认用真实状态反馈，说明需要用户做什么
纠正与返回可以修改什么，会影响哪些步骤解释变更范围，保留已发生的事实
打断与停止停止的是播报、当前步骤还是整个任务区分控制对象，及时终止可停止的后续动作
恢复与接续从哪里继续，哪些条件已变化检查上下文、授权和状态，不盲目重放

8.1 多模态共享语义

“这个”“继续”“停一下”等表达，需要绑定当前焦点、会话与任务。语音、手势和界面事件可以互相补充；模态切换不应凭空创建另一套任务事实。

8.2 眼镜上的注意力原则

系统根据用户活动、现实环境、隐私与任务紧急度，决定信息是即时呈现、轻提示、延后还是静默保留。服务提出呈现需求，系统协调输入焦点、视觉、音频与触觉。

重要控制不应被皮肤或自定义布局隐藏；同一个动作的基本含义不应因服务而颠倒。个性化主要改变表达和组织方式，同时保留可学习的系统秩序。

09 · 服务管道：Create–Use–Improve

9.1 Create：把需求变成完整服务

表达需求 → 澄清目标 → 选择或创建积木 → 组织行为与数据 → 选择容器与交互 → 预览与试用 → 保存服务定义。

AI 创作助手补全必要结构：触发条件、能力依赖、数据作用域、权限、异常、任务控制与结果表达。用户围绕目标和体验作选择，不必亲自承担所有专业分工。

创作的产物必须包含可运行的行为定义。只有界面、静态卡片或一段生成代码，都不足以代表完成服务创作。

9.2 Publish：让服务成为可识别的对象

定义检查 → 依赖与权限声明 → 行为预览 → 形成版本 → 选择私用或分发。

私用、受邀分享与公开市场可以采用不同审查要求；它们都需要遵守设备与数据边界。公开审核解决分发可信度，不能替代每一次运行中的授权判断。

9.3 Use：以真实任务兑现目标

触发 → 理解与路由 → 建立任务 → 取得必要授权 → 执行与等待 → 记录实际结果 → 选择合适视图反馈。

使用阶段必须覆盖能力不可用、等待外部响应、部分成功、用户纠正与停止。系统不能将“已生成界面”“已提交请求”或“模型认为完成”当成目标已完成。

9.4 Improve：从使用回到创造

使用反馈 → 调整目标或规则 → 预览差异 → 形成新版本 → 用户选择更新。

任务内的一次纠正，不自动修改整个服务，也不自动写入长期偏好。用户可以选择只影响这一次、成为服务默认，或保存为个人偏好。旧任务与新版本的关系应清楚可见。

10 · 连接协议：自由组合的共同底座

10.1 五类连接

连接类型表达什么必须保留的语义
数据输入输出如何匹配类型、版本、单位、数量、时间、来源与数据域
事件什么发生了，何时唤醒来源、身份、时效、订阅范围与重复事件处理
控制如何继续、暂停或取消目标任务、当前状态、作用范围与授权
结果实际执行到什么程度接受、进行中、完成、失败、部分成功与无法确认
视图如何呈现与回传操作服务与任务绑定、状态版本、动作对象与焦点

输出与输入不兼容时，需要明确转换。自然语言可以帮助解释和配置连接，但不能替代类型、身份和授权关系。

10.2 同一任务，多种表达

一个任务具有明确身份和一致的有效状态。窗口、Widget、VUI 等视图可以只展示部分信息，但不能各自决定与其他视图冲突的执行事实。

来自视图的操作首先是请求；通过任务规则与权限判断、取得实际结果后，才成为新的任务状态。旧视图中的操作需要检查是否仍然适用。

10.3 不同服务，明确协作

服务之间应声明可提供的数据、可订阅的事件、可触发的动作，以及各自的权限和生命周期。跨服务协作可以形成关联任务；原有数据边界与用户选择仍然有效。

连接器负责外部系统的身份与协议语义，动作负责实际改变。外部返回内容是数据，不能自行变成新的系统指令或授权。

11 · 任务、状态与生命周期

11.1 运行事实与交互状态分开

服务定义回答“可以做什么”；任务回答“这一次在做什么”；视图回答“当前如何表达”。系统应持续区分这三类事实。

任务至少能够表达：待处理、进行中、等待输入、等待外部结果、暂停、完成、部分完成、失败与取消。无法确认的外部结果应被明确标记，不能默认按成功或失败重试。

11.2 控制对象必须清楚

用户动作作用对象与含义
收起或关闭视图改变显示与焦点；不自动等于任务停止
暂停任务暂停允许暂停的后续步骤；已发生动作保留
停止任务停止可取消的执行，说明已完成部分与仍在途的动作
停用服务不再接受新的触发；已有任务如何处理需明确
撤销权限后续能力调用失去授权；正在进行的动作按实际可取消性处理
删除数据按所选作用域与保留规则删除；不等同于关闭界面
更新或回退版本改变服务定义；不自动撤销已经发生的外部动作

11.3 连续性有边界

跨视图、跨设备或断连恢复时，保持任务身份、已完成事实与控制归属。继续之前重新确认必要的授权、数据时效和能力可用性；不能恢复时解释原因，并提供可理解的下一步。

重复触发、重试与多端接续不应无意制造重复动作。同一个会改变外部状态的步骤，需要明确的执行归属和结果记录。

12 · 用户主权与系统治理

12.1 用户保有的权利

  • 选择从现成服务开始，或自行创造和定制。
  • 选择服务、工具、提供方与交互方式，并理解相关差异。
  • 决定授权范围、委托程度和持续时间，随时调整后续权限。
  • 查看与修改系统理解的目标、服务规则和个人偏好。
  • 知道任务真实状态，纠正、停止或接续自己的委托。
  • 管理服务数据与个人记忆，决定保留、分享和删除。

12.2 数据域彼此独立

当前上下文、任务记录、服务数据与个人记忆具有不同目的和生命周期。临时观察或模型推断不自动成为长期画像。跨服务使用数据、将本地信息交给远程服务，或将试验内容公开，都需要符合相应授权。

12.3 信任不能由界面伪造

系统授权提示、执行状态和关键控制应与服务自定义内容保持可辨别的归属。模型可以组织表达，不能改写实际回执；第三方内容不能冒充系统权限决定。

12.4 治理是持续规则

权限、注意力、资源、隔离和版本规则贯穿创作、发布、安装、运行与退出。服务只获得完成目标所需的能力；新增敏感能力或扩大行为范围时，用户应重新拥有选择机会。

13 · 开放生态：创建、自用、审核、市场

13.1 开放的不只是服务，也包括积木

普通用户可以提出需求并组合现成能力；进阶创作者可以制作新的能力封装与服务模板；开发者可以编写能力、连接器或独立 SDK 应用。

一块由用户创建的积木，可以先被自己使用，再选择分享、提交审核与进入市场。系统为不同创作深度提供指导，而不要求所有用户走同一条专业开发路径。

13.2 四个阶段，四种含义

阶段核心含义
创建形成能力或服务定义，声明接口、依赖、行为与边界
自用在本人授权范围内试验与日常使用，不自动公开内容和数据
审核对公开分发的身份、内容、权限、依赖与行为进行审查
市场让他人发现、理解、选择和安装，维护版本、支持与退出机制

私用也遵守系统运行边界；审核通过也不能取代用户授权。市场评价、作者身份与权限范围应帮助用户作选择，而非只展示一个好看的封面。

13.3 分发对象保持清楚

能力包定义可复用能力，服务包定义完整服务，模板帮助创建新服务，SDK 应用承载独立体验。不同对象可以关联，但不能用同一种安装描述掩盖它们不同的权限、运行方式和更新影响。

14 · 核心设计澄清

需要澄清的问题Lego OS 的设计回答

约束贯穿全程，保证系统可以被信任。治理不是用户可随意组合绕过的普通积木；服务只能声明需求和接受决策。

ID积木输入输出契约与边界
G01权限与数据域验证Call + PolicyContextAllow / Deny / Ask发布、安装与每步执行都验证，撤销立即影响后续调用。
G02注意力与焦点仲裁OutputRequest + ContextPresentationDecision输入焦点、音频、视觉优先级按情境协调。
G03资源预算与降级ResourceEstimate + TelemetryBudgetDecision预检不代替运行监测；温升与内存压力先降表现再暂停。

G05版本与发布控制ValidatedPackageReleaseId / RollbackState私有发布、灰度与回退；实例锁定版本。
